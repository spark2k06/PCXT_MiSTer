# Adapting the core to an 8086: source of truth

An OSD option to run the machine as an 8086 instead of an 8088, applied with
Reset & Apply, with no hacks. This document is the reference the work is done
against: what the real hardware did, what a known-good software implementation
does, what this core already has, and what is actually left to build.

It is deliberately not a plan. The plan is at the end, and it is short, because
most of the value here is in knowing which parts are *not* problems.

---

## 1. The one thing to understand first

An 8086 differs from an 8088 in exactly two ways:

* **External data bus** — 16 bits instead of 8.
* **Prefetch queue** — six bytes instead of four, filled two at a time.

Everything else is identical: same registers, same instruction set, same
microcode-visible behaviour, same segment model. There is no third difference
hiding somewhere.

That sounds like it makes this easy. What made it hard *in real hardware* was
something this core mostly does not have.

### Why real 8086 XT-clones were complicated, and why we are not

On a real PC/XT-compatible board, memory and peripherals both hang off the same
8-bit expansion bus. Giving that machine an 8086 means the motherboard has to
convert every 16-bit CPU transfer into whatever the 8-bit bus can carry, and
convert it back. From the VCFED thread:

> "Those control signals need to be generated by the motherboard — that's
> probably the number one reason why 8086 motherboards are more complex than
> 8088 ones."

The mechanism, in discrete logic: an extra 74ALS245 to move a byte between the
high and low halves of the data bus, plus a 74ALS373/74ALS245 pair on the low
eight bits to latch even-addressed bytes. `BHE` and `A0` together say which
half of the bus a byte is on, and the steering network crosses `D8-D15` onto
`D0-D7` when an 8-bit peripheral is addressed at an odd address. The Olivetti
M24 did the decode with an 82S123 32×8 bipolar PROM. The IBM AT later replaced
the 245/373 pair with a single 74ALS646.

**None of that applies here**, and the reason is worth stating precisely:

| | real 8086 XT-clone | this core |
|---|---|---|
| Memory | on the 8-bit expansion bus | SDRAM behind `RAM.sv`, not on the ISA bus at all |
| Peripherals | on the 8-bit expansion bus | on the chipset's 8-bit bus, unchanged |
| Byte steering | discrete 245/373/PROM network | a byte-lane select in `RAM.sv`, already written |

Our memory is *not* on the byte bus. So the 16-bit path we need is a private
one between the CPU core and `RAM.sv`, and the expansion side can stay eight
bits wide for ever — which is what an XT-class 8086 machine looked like from
software's point of view anyway.

### The precedent that matches us exactly

From the same thread, on the 8086-based PS/2 Model 30:

> "The 8086 ps/2's alternately store high and low bytes of a word between
> separate banks of ram."

That is an architecture this core briefly tried — byte N in lane N[0] of SDRAM
word N>>1 — and then reverted because the machine would not boot with it.

The short version, because it governs everything below: writing one byte into
half of a 16-bit word requires the SDRAM's byte write mask, `DQML`/`DQMH`. On
this hardware that mask does not appear to work. A diagnostic build proved the
upper data lane reads back correctly and that duplicating the byte across both
halves is sound, at every speed; only masking one lane fails.

That still blocks the repacked layout, but no longer blocks the 8086 path.
`RAM.sv` keeps the proven layout — one emulated byte in the low lane of each
SDRAM word — and transfers two consecutive SDRAM words in one burst. A read
takes the low byte of each beat; a write presents the CPU word's low and high
bytes on successive beats. No byte mask is involved.

### The precedent that is a warning

Also from the thread, on the Olivetti M24:

> "The way the M24 splits 16bit transfers into two 8-bit cycles is not
> compatible with IBM's."

It needed a "bus correction kit" to run IBM software properly. The lesson is
concrete: **the danger in this project is not the 16-bit path, it is what
happens to the transfers that are still split.** Getting the fast case right
and the split case subtly wrong is exactly how the M24 failed.

## 2. Reference implementation: 86Box

86Box implements the 8086 as a flag, `is8086`, set once at
`src/cpu/cpu.c:529` (checkout at `D:\GitHub\86Box`):

```c
is8086 = (cpu_s->cpu_type > CPU_8088) && (cpu_s->cpu_type != CPU_V20)
                                      && (cpu_s->cpu_type != CPU_188);
```

Note what that excludes: the **V20 is not an 8086** for bus purposes. It has an
8-bit bus like the 8088. (The 16-bit NEC part is the V30.)

There are two BIU implementations. `808x.c` is the older one; `vx0_biu.c` is the
newer, cycle-driven one and is the better model. Where they differ, follow
`vx0_biu.c`.

### 2.1 The complete list of places `is8086` changes behaviour

Five, and that is all of them:

| What | `vx0_biu.c` | Rule |
|---|---|---|
| Memory word read | `readmemw_vx0`, ~837 | even address → one wide cycle; else two byte cycles |
| Memory word write | `writememw_vx0`, ~920 | same |
| I/O word access | `bus_do_io`, ~755/776 | even port → one wide cycle; else two byte cycles |
| Prefetch fill | `pfq_write`, ~968 | word fetch **only when `pfq_ip` is even** |
| Queue depth | ~232, ~525 | 6 bytes, refill while `pfq_pos < 5` |

### 2.2 Memory word access, exactly

```c
if (is8086 && !(a & 1)) {
    bus_request_type = BUS_MEM | BUS_WIDE;      /* one bus cycle */
    biu_begin_eu();
    biu_wait_for_read_finish();
} else {
    bus_request_type = BUS_MEM | BUS_HIGH;      /* first byte cycle  */
    ...
    bus_request_type = BUS_MEM;                 /* second byte cycle */
    ...
}
```

Two things to carry across:

* The alignment test is on the **offset**, `a`, not the linear address. A word
  at an odd offset is split even if the linear address happens to be even.
* In the split path the older `808x.c` shows the address arithmetic explicitly:
  `(a + 1) & 0xffff` — the second byte's offset **wraps inside the segment**.
  A word read at offset `0xFFFF` takes its high byte from offset `0x0000` of
  the same segment. Our BIU already does this (`addr_out_temp_offset` is 16
  bits and simply increments), so this is a box already ticked.

### 2.3 Prefetch, and the detail the old BIU gets wrong

```c
/* Byte fetch on odd address on 8086 to simulate the HL toggle. */
int fetch_word = is8086 && !(pfq_ip & 1);
```

`808x.c` fetches two bytes unconditionally; `vx0_biu.c` fetches a **single
byte** when the fetch pointer is odd, which is what a real 8086 does after a
jump to an odd address — it takes one byte to get back into alignment and is
word-aligned from then on.

Follow `vx0_biu.c`. Getting this wrong means every fetch after an odd jump
target reads a byte the queue then has to discard, which is both slower and a
correctness hazard if anything else keys off the fetch address.

### 2.4 I/O

86Box widens even-port word I/O for the 8086. **We should not**, and this is a
deliberate divergence, not an oversight: our peripheral bus is eight bits wide
and stays that way, exactly as an XT-class expansion bus was. On real 8086
XT-clones a 16-bit I/O access to an 8-bit card *was* split into two byte cycles
by the motherboard's steering logic. Keeping I/O as two byte cycles is the
faithful behaviour for this machine, and it keeps `Peripherals.sv` and the
whole ISA path out of the change entirely.

## 3. What this core has today

### 3.1 Already done

The memory layout is **not** in this list any more; see §1 and step 0.

* **The 16-bit interface between EU and BIU.** This is the surprise, and it is
  good news. The EU already issues *word* requests — `mcl86_biu_max.sv` has
  command codes `0x10` mem word read, `0x13` mem word write, `0x1A`/`0x1C` I/O
  word — and `BIU_RETURN_DATA` is already 16 bits. The BIU **splits** them,
  with `word_cycle` ("This request is a word: run two byte cycles") and
  `byte_num` selecting the half, hopping through state `0x50` for the second
  byte and assembling the result at state `0x09`.

  An 8086 BIU is therefore not a rewrite. It is **not doing the split** when
  the offset is even.

* **Segment-wrapping address arithmetic**, as above.

* **Some of the speed benefit is already banked - but much less than it looks.**
  The read lookahead can serve the second byte of a word access from its latch
  instead of the SDRAM. Measured in the chipset bench at the maximum setting,
  in chipset clocks from MEMR: a cold read releases the CPU at 10, a latch hit
  at 4.

  **The latch had one entry until 2026-08-21, and every read that was allowed
  to park overwrote it - including instruction fetches**, which are memory reads
  like any other. So it only helped where the bus was doing one thing at a time:
  a `REP` string operation, or a straight run of fetch. It has two entries now,
  which fixed that; see the section below for what it was worth and, more
  importantly, for the bound it established.

  | word memory read at `2'b11` | chipset clocks | 16-bit cycle | saving |
  |---|---|---|---|
  | inside a `REP` string op, second byte hits | 10 + 4 = 14 | 10 | **29%** |
  | in ordinary interleaved code, both miss | 10 + 10 = 20 | 10 | **50%** |

  So the earlier "29%, not the 50% that twice the bus width suggests" was right
  only for string operations. **For ordinary code the full 50% is there**, which
  makes the 16-bit path worth more than this document first claimed.

### 3.2 Hardware validation outcome

The step 5/6 RBF has now booted and run successfully on MiSTer in both CPU modes
at 4.77, 7.16, 9.54 MHz and Max. This includes the corrected late read
sample at 9.54 MHz. RAM, video and I/O remain functional, and reset correctly
applies the selected CPU type.

A paired hardware timing run then settled the remaining timing question. At all three
fixed speeds, an aligned `READW` is about 20% faster in 8086 mode, while the odd
`READWO` and the byte-oriented `READ`, `WRITE` and `COPY` controls do not move.
The aligned saving normalises to 3.62, 4.22 and 4.29 CPU clocks per word at
4.77, 7.16 and 9.54 MHz respectively: the fingerprint of removing one
approximately four-clock byte bus cycle.

### 3.3 Where instruction time actually comes from

MCL86 deliberately shares its execution unit and microcode between the 8088
and 8086. The EU supplies the instruction's nominal execution floor through
`clock_cycle_counter`, while the BIU supplies costs that depend on the real
transfer: queue starvation, one or two bus cycles, READY waits and target
width. The EU does not need a second timing table merely because the external
bus is wider.

The earlier assumption that the microcode had the 8088 word-split penalty baked
in was therefore too strong. Hardware disproves it: if the counter had already
charged that penalty unconditionally, suppressing the second cycle could not
make aligned `READW` about four clocks faster at the fixed speeds. Conversely,
the unchanged odd-word result proves that the implementation has not applied a
blanket instruction-time discount.

At **Max** `cycle_accrate` is 0 and the nominal counter is bypassed, so
the BIU dominates more directly. At the fixed speeds both pieces remain active:
the shared EU establishes the nominal timing and the selectable 8088/8086 BIU
adds the transfer costs that actually occur.

**Consequence:** step 7 is a validation phase, not an implementation phase for
a second microcode timing model. Intel documentation and an independent
emulator such as 86Box remain useful comparison oracles, but current evidence
does not justify adding or selecting another set of timing constants.

## 4. The safe path

Ordered so that each step is independently verifiable and independently
revertible, and so that the step most likely to fail comes as early as its
dependencies allow.

| # | Step | Verified by | Reversible |
|---|---|---|---|
| 0 | **Establish whether the SDRAM byte write mask works at all** | a hardware build; simulation cannot see this | — |
| 0b | **Memory repacking** — two bytes per SDRAM word | `ram_lookahead_tb`, `ram_refresh_collision_tb`, four mutation checks | ⛔ **written and reverted, 2026-08-21 — blocked on step 0** |
| 1 | Widen `RAM.sv`'s read path to expose the full word alongside the existing byte | `ram_lookahead_tb`, twelve word cases + five mutations | ✅ **done** |
| 2 | Carry the word to the CPU — a private 16-bit path through `Chipset.sv`, leaving the 8-bit bus untouched | the decode in `ram_lookahead_tb`; the wiring by elaboration only, see below | ✅ **done** |
| 3 | Queue: 6 bytes with a working full/empty scheme, **still fetching one byte at a time** | `biu_prefetch_tb`, at both depths, plus three mutations | ✅ **done** |
| 4 | Word-aligned prefetch (`fetch_word = is8086 && !(pfq_ip & 1)`) | `biu_prefetch_tb` for alignment/queue behaviour; `biu_ram_prefetch_tb` for the real BIU→RAM→SDRAM path | ✅ **done** |
| 5 | Suppress the split in `word_cycle` when the offset is even | `biu_prefetch_tb` for even/odd/map/I/O/8088 fallback; `ram_lookahead_tb` and `biu_ram_prefetch_tb` for two-beat write/read data | ✅ **done** |
| 6 | OSD option + Reset & Apply plumbing | `cpu_type_latch_tb`, `cpu_8086_speed_tb`; build/boot in both modes and every speed on hardware | ✅ **done** |
| 7 | Validate shared-EU / selectable-BIU 8086 timing at 4.77 / 7.16 / 9.54 MHz | paired hardware timing measurements plus an extended instruction/bus regression in both CPU modes | ✅ **done** |

Steps 3 and 4 are worth doing before 5 because a deeper, correctly-aligned
queue is a *behaviour-preserving* change that can be proven on its own. If the
queue rework is going to fight, better to find out while nothing else has moved.

### Step 3: eight entries, and depth enforced separately

The original scheme selected the entry with `pfq_addr_in[1:0]` and told full
from empty with bit 2 as a wrap bit. That only works when the depth is exactly
the index modulus, which is why six looked structurally awkward.

Separating the two makes it ordinary. There are now **eight physical entries**,
`[2:0]` of the pointer picks one, and depth is enforced by how many bytes the
queue is allowed to hold:

```systemverilog
assign pfq_depth = IS8086 ? 4'd6 : 4'd4;
assign pfq_used  = pfq_addr_in[3:0] - pfq_addr_out[3:0];
assign pfq_full  = (pfq_used >= pfq_depth);
assign pfq_empty = (pfq_used == 4'd0);
```

Two arguments make that subtraction safe. `pfq_used` is always between zero and
the depth - the read pointer only advances when the queue is not empty, the
write pointer only when it is not full, and a jump sets both to the same value -
so four bits carry the true count even across the 16-bit wrap. And two live
bytes can never share an entry, because their pointers differ by less than
eight. Neither argument depends on the depth being a power of two, which is the
whole point.

Cost: four extra bytes of register. Six entries would have needed a modulo-6
index; eight needs none.

**`IS8086` exists from here on.** It is a real input to `mcl86_biu_max` and to
the `i8088` wrapper, hardcoded to 0 at the top level, so steps 4 and 5 have a
signal to hang off and step 6 is only OSD plumbing. The bench drives it as a
runtime input and checks four, then six, then four again - a depth that stuck at
six after switching back would be an 8088 running ahead of itself.

Mutation-checked three ways: depth ignoring `IS8086`, `pfq_full` off by one, and
the old four-entry index kept with the new depth. That last one is the case that
says eight entries are actually required: with four entries and a depth of six,
the 8088 cases still pass and only the 8086 ones fail, on aliased bytes.

### Step 2, and the signal the CPU needs before it can use any of this

The word runs *beside* the 8-bit bus, not through it. `data_bus_word` has one
source and one destination and never joins the byte multiplexer, because putting
it there would mean handing every other device a 16-bit port it has nothing to
put on.

That leaves a question the CPU cannot answer on its own: **only SDRAM can be
accessed wide.** Video memory, the BIOS ROM, an unmapped EMS frame, the UMB window
when it is off - a wide read at any of those would come back holding whatever
`RAM.sv` last had, with no bus cycle to show for it. So `Chipset.sv` exports
`word_read_possible`, straight off `ram_address_select_n`, combinational on the
latched address and therefore settled long before the CPU has to commit.

The division of labour is deliberate: `word_read_possible` is about the memory
map alone, and the CPU still checks that the access is a word at an even address
- the half of the question it is the one that knows. Step 5 consults both.

This also means an 8086 here does word accesses to video memory as two byte
cycles. That is not a shortcut: on a real 8086 XT-clone the motherboard's
steering logic split a 16-bit access to an 8-bit card into two byte cycles too,
which is the same reason §2.4 keeps I/O eight bits wide.

**A gap worth naming.** `Chipset_tb` was the obvious place to test this and it
does not build - the vendored sound sources use assignment patterns on unpacked
`wire` arrays that Icarus rejects, which `run_tests.sh` has documented for a
while. Tests written there would have looked like coverage without ever running,
so the decode is tested in `ram_lookahead_tb` against `ram_address_select_n`
instead, and the Chipset wiring is covered by Quartus elaboration only. Making
`Chipset_tb` build again is its own piece of work and would pay for itself
across the rest of this table.

### Step 5: request first, suppress the split only after decode

The BIU knows at dispatch whether an EU memory request is a word at an even
offset, but the chipset only knows whether the resulting physical address is
SDRAM after T1 has latched it. The implementation preserves that division:

* an even 8086 memory word raises a private read or write candidate alongside
  the ordinary first byte cycle;
* RAM ignores the candidate if its address decode is not selected;
* after T1, `word_read_possible` tells the BIU whether the candidate was valid;
* accepted candidates return or write both bytes and finish after one bus
  cycle; rejected candidates clear the request and run the original second
  byte cycle.

The offset test is intentionally on the EU's 16-bit offset, not the linear
address. Odd words therefore retain the existing segment-wrapping split. I/O
words never raise either private request and remain two byte cycles.

Writes need no SDRAM byte mask. `RAM.sv` freezes the complete CPU word when it
accepts the command, requests a two-word KFSDRAM burst, and selects the low byte
for beat zero and the high byte for beat one. Both bytes occupy the low lanes
of their existing consecutive SDRAM words, so the memory layout is unchanged.
The lookahead entries for both addresses are invalidated at acceptance.

### Step 6: select now, apply on reset

The `System & BIOS` OSD page now exposes `CPU Type: 8088 / 8086` in
`status[63]`, the last unused status bit. Zero means 8088, preserving the
existing machine and persisted-config default. The raw OSD bit is deliberately
not wired directly to the BIU.

`cpu_type_latch` tracks the requested value throughout the core's stretched
reset and freezes it when reset ends. A menu change while software is running
therefore remains pending until `Reset & apply settings` asserts `status[0]`.
The reset clears the BIU and queue before the selected depth and bus width can
be observed, so no instruction can see a mid-flight CPU-type change. The same
path also applies the persisted selection during initial core startup.

`cpu_type_latch_tb` checks the 8088 power-on default, both mode transitions,
changes made while running, and changes made while reset remains active.

**Hardware validation finding (2026-08-22).** The first step 5/6 RBF booted and
ran in 8088 mode and in 8086 mode at 4.77 MHz, 7.16 MHz and maximum. An 8086
cold boot with 9.54 MHz already selected did not start the BIOS, even after an
explicit Reset & Apply. This ruled out a malformed live speed transition.

`cpu_8086_speed_tb` was added around the complete microcoded CPU, the real
`XT_CE_Generator`, `KF8288`, `READY`, `RAM.sv` and the SDRAM controller/model.
Its real-mode program starts at `FFFF:0000`, crosses the reset-vector jump and
performs verified aligned word reads and writes while instruction prefetch is
active. It passes all four cold-start profiles and the live transitions
4.77→9.54, 7.16→9.54 and maximum→9.54. A 0–9 ns sweep of the 100 MHz clock phase
against the 50 MHz chipset clock also passes at 9.54 MHz. The smaller
`biu_ram_prefetch_tb` now independently sweeps all four profiles as well.

Consequently the hardware failure was **not reproduced by zero-delay RTL**.
Quartus can generate a post-fit functional `.vo` for this Cyclone V, but not a
delay-annotated `.sdo`/`.sdf`; Intel directs Cyclone V timing diagnosis to
TimeQuest instead. Targeted TimeQuest reports showed that the registered 16-bit
RAM path had about 5.8 ns of setup margin, while the old byte-return path into
the BIU had only 0.331 ns in its worst reported crossing. At 9.54 MHz RAM
lookahead is enabled but, unlike Max, reads were still sampled on the
earlier CPU edge.

The permanent fix keeps the 9.54 MHz cycle profile and zero extra RAM wait
cycles, but sets `shift_read_timing` so the BIU samples read data on the later
edge, as Max already does. A diagnostic RBF with only that behavioural
change passed on MiSTer in both 8088 and 8086 modes at 9.54 MHz, as well as at
all remaining speeds. In particular, 8086 + 9.54 MHz now cold-boots and runs
normally. The fix also passed `biu_ram_prefetch_tb` and the full
`cpu_8086_speed_tb`.

That A/B hardware result identifies the early read sample as the cause and
clears steps 5 and 6. It also separates the issue from the new aligned 16-bit
path: delaying the shared read capture fixes the machine without disabling wide
prefetch or wide data cycles. The project still has unrelated global setup
violations in TimeQuest, which remain timing-closure debt, but the working RBF
was built with those violations and step 7 is no longer blocked by this fault.

### Step 7: validate 8086 timing at the fixed speeds

**Entry condition: satisfied.** The exact step 5/6 build completed synthesis
and has booted and run in both CPU modes at every speed on MiSTer. The 9.54 MHz
read-sampling correction was also verified in both modes. This freezes a
known-good wide-bus baseline before extending the timing regression.

The first step-7 hardware comparison used the same timing binary in 8086 and
8088 modes:

| test and CPU | 4.77 MHz | 7.16 MHz | 9.54 MHz | MAX |
|---|---:|---:|---:|---:|
| `READW`, 8086 | 14789 | 10563 | 8700 | 4723 |
| `READW`, 8088 | 18491 | 13445 | 10899 | 6163 |
| `READWO`, 8086 | 18477 | 13435 | 10891 | 6162 |
| `READWO`, 8088 | 18491 | 13444 | 10898 | 6165 |

`READW` performs 4096 aligned word transfers. Converting its paired PIT-tick
difference with CPU/PIT ratios 4, 6 and 8 gives an 8086 saving of 3.62, 4.22
and 4.29 CPU clocks per word. `READWO` differs by only 0.014 clocks per word at
each fixed speed. Byte RAM, video and I/O controls are likewise effectively
unchanged. This is the expected result of one wide cycle for aligned SDRAM and
two byte cycles everywhere the XT-class machine cannot widen the transfer.

This result validates the central architecture:

* the common MCL86 EU/microcode supplies a timing floor usable by both CPUs;
* aligned SDRAM word accesses receive the 8086 cost by completing in one cycle;
* odd words still pay two cycles, including segment wrap at `FFFFh`;
* video, I/O and every non-SDRAM target retain their XT-class byte-cycle cost;
* READY-generated wait states remain additive;
* queue starvation, odd-target fetch alignment and EU/prefetch overlap remain
  observable rather than being folded into a blanket correction;
* Max remains unchanged because `cycle_accrate == 0` bypasses the
  nominal timing counter.

No separate 8086 timing source or RTL timing change is justified by these
measurements. Intel data and 86Box remain comparison oracles, not a replacement
timing model to transplant.

`cpu_8086_timing_tb` completes the remaining coverage around the full
microcoded EU+BIU CPU, the real `XT_CE_Generator` profiles and `KF8288`. Its GNU
assembler workload places twelve observable boundaries around:

* register-only execution;
* aligned and odd word reads;
* aligned and odd read-modify-write operations;
* PUSH/POP and near CALL/RET stack traffic;
* aligned and odd `REP MOVSW`;
* a loop whose branch target is deliberately at an odd IP;
* word `IN` and `OUT` on the XT-class 8-bit I/O bus;
* an external maskable interrupt, both INTA cycles, its stack frame and IRET.

Every workload runs as an 8088 and an 8086 at 4.77, 7.16, 9.54 MHz and maximum
speed. The bench compares functional signatures, CPU-clock intervals and the
completed FETCH/MEMR/MEMW/IOR/IOW/INTA cycles between every pair. It asserts
that the 8088 never requests a wide data cycle; aligned 8086 operands reduce
the data-cycle count; odd operands do not; word I/O remains split; and the
external interrupt performs exactly two INTA cycles. The ideal low-RAM model
keeps that accounting independent of SDRAM implementation latency, while
`cpu_8086_speed_tb` and `biu_ram_prefetch_tb` retain coverage through READY,
`RAM.sv` and the SDRAM controller/model.

The complete `rtl/8088/TESTBENCH/run_tests.sh` suite passes **6/6** benches,
including all four paired timing profiles. Together with the paired hardware
hardware result, every observed difference is explained by prefetch, the
number of bus cycles or target width, with no 8088 regression. **Step 7 is
complete.**

The frequencies describe this core's profiles: 4.77 MHz is close to a 5 MHz
8086, 9.54 MHz is close to a 10 MHz part, and 7.16 MHz is an accelerated
non-standard profile. Cycle behaviour can still be 8086-accurate where the
selected frequency is not a historical Intel speed grade.

### Step 1 did not need the repacking after all

Step 1 was written assuming step 0b: with two emulated bytes per SDRAM word, a
word read would return both lanes of one word. Step 0b is blocked, so that route
is closed - but the step turned out not to need it.

`RAM.sv` already fetches two consecutive bytes in **one** SDRAM transaction. It
has done since the lookahead landed: `access_num = 2` issues a two-beat burst,
the first beat is the byte the CPU asked for and the second is the byte after
it. Until now the second beat was parked in the latch on the guess that someone
would want it. A word read simply asks for the burst on purpose and hands both
beats over.

So the 16-bit *read* path costs one register and a mux, not a memory remap. The
byte layout in SDRAM is untouched: one emulated byte per 16-bit word, exactly as
today, with the upper lane still unused.

**The evenness argument, which is what makes it safe.** The burst is only
correct when the two columns are in the same row, because KFSDRAM's column adder
is nine bits and wraps inside the row. That is the `!= 9'h1FF` test the lookahead
already carries. For a word read it needs no test at all: word accesses are
always at even addresses - an 8086 splits an odd one into two byte cycles, and
offset parity equals linear parity because a segment base is always a multiple
of 16 - so the first column is even, at most 510, and the second is at most 511.
The same evenness rules out straddling an EMS, UMB or video decode boundary,
since every one of those is 16KB-aligned and therefore at an even address.

`RAM.sv` carries a `translate_off` check that shouts if a word is ever requested
at an odd address, because the failure it would cause is a once-per-512
corruption rather than anything that shows up immediately.

**What step 1 deliberately does not do:** a word read takes no lookahead hit
(the latch can only hold one half of a word, so a hit on the low byte would
leave the high one unfetched) and parks nothing (the second byte was delivered,
not guessed at, and spending an entry on a byte the CPU already holds would
evict something useful). Both are asserted in the bench, and both were confirmed
by mutation - the version of the hit case written first primed the latch at the
wrong address and let the mutation through.

It is also **not gated on `clk_select`**. The burst gate exists to keep a
throughput guess out of the cycle-accurate settings; a word the CPU actually
asked for is not a guess, and an 8086 has a 16-bit bus at every speed.

### The cheaper thing, tried - and what it settled

The eviction above suggested a change far smaller than any step in the table:
give the latch **two entries**. That was built and measured before committing to
any of the work below, and it is done - `RAM.sv` carries two entries with
round-robin replacement, which needs no signal from the BIU at all, because the
code and data streams alternate on the bus by themselves and therefore land in
different entries. (Routing the max-mode status from `mcl86_biu_max` was
considered and rejected: it returns to passive in T3 and does not describe the
cycle during DMA, so it would have needed latching and qualifying to do a job
that round-robin does for free.)

**Result, on hardware:** `MISSRD - HITRD` went from 10 ticks to 315 at the
maximum setting, which is 1.61 CPU clocks saved per hit at 25 MHz. `MISSRD`
itself improved 1.2%. `READ`, `READW` and `FETCH` did not move, which is
correct - they are single-stream tests where one entry was already enough. The
full table lives with the timing measurements.

**What it settled, and this is the part that matters here:** at 9.54 MHz nothing
moved at all, to the tick, even though the lookahead is enabled there. The
reason is structural rather than incidental - `cycle_accrate` is 1 at every
setting below maximum, so the cycle counter pads the bus cycle out regardless. A
cold SDRAM read is ~200 ns against a 419 ns bus cycle at 9.54 MHz; the
transaction already fits with room to spare.

**No latency optimisation of any kind can show below the maximum setting.** That
is a permanent bound on this whole class of change, and it means the 16-bit path
is not a latency optimisation if it is to be worth anything at the cycle-accurate
speeds: its value there has to come from the microcode charging fewer clocks per
word transfer, which is exactly the `READW`/`READWO` question in step 3 below.

### What the same run says about where the time is

`FETCH` meets 16384 bytes once, so its tick count divides straight into a
per-byte cost:

| | CPU clocks/byte | ns/byte |
|---|---|---|
| 4.77 MHz | 4.38 | 918 |
| maximum (25 MHz) | **9.71** | 388 |

At 4.77 MHz a fetched byte costs the textbook 8088 bus cycle of 4 clocks. **At
maximum it costs 9.71** - roughly 5.7 clocks of wait per byte, of which the
SDRAM transaction is about half and the four-T-state bus cycle itself is the
rest.

This strengthens the case for the 16-bit path beyond what the 29%/50% table
above claims. That table costed the *transaction*. The bus cycle is the bigger
term at maximum, and a 16-bit path halves the **number of bus cycles**, not just
the bytes per transaction - so on the fetch path, which this measurement shows
is where maximum-speed time goes, it is worth close to the full 2x.

### Where it could still go wrong

* **`clk_100` timing.** It closes at 91.68 MHz against a 100 MHz constraint —
  it already fails today. Every step above adds logic to that domain. This is
  the residual risk that cannot be designed away, only measured after each step.
* **The split path, per the M24 warning.** Odd-offset word accesses must keep
  behaving exactly as they do now. Any bench for step 5 must assert the odd
  case as hard as the even one.
* **DMA and the HPS BIOS loader** both write through `RAM.sv` via the arbiter
  as byte accesses. They must stay byte accesses. Verified as unaffected by the
  repacking; must be re-verified after step 2 widens the path.

## 4b. Evaluated and parked: a hardware effective-address adder

The 80186 added dedicated BIU hardware to compute the effective address, where
the 8086 walked it through sequential microcode at a cost of 5-12 clocks. The
same idea was considered here and is **not worth doing before the work above**.
The numbers are recorded so the question does not have to be re-argued.

**MCL86 does not do what a real 8086 did.** The microsequencer has seven jump
sources and three of them are addressing-mode tables
(`mcl86_eu_core.sv`, the jump-source comment):

```
2 - mod/reg/rm dispatch: imm | MOD | RM, the addressing-mode table
4 - EA register fetch table, keyed on the BIU's decoded operand
5 - EA register writeback table, same key
```

The ModRM byte *is* part of the jump address, so reaching the right routine
costs one jump, not a search. What remains is the arithmetic itself — two adds
through `mcl86_adder` for something like `BX+SI+disp` — not the original's
decode-and-sequence.

**Those steps already run about twenty times faster than the bus they feed.**
The microsequencer is clocked by `CORE_CLK_INT`, which is `clk_100`, not the
emulated CPU clock; the BIU header says so in as many words. At the maximum
setting one emulated T-state is two chipset clocks, 40 ns, so two or three adds
at 100 MHz is under a single T-state. The 80186 saved 5-12 *CPU* clocks. Here
the equivalent saving is a fraction of one.

**Three obstacles, worst first:**

1. **The microcode has no source in this tree.** `mcl86_ucode.mem` is a 4K×32
   binary with no table and no assembler beside it, so the EA routines cannot be
   rewritten. It would have to be a short-circuit: recognise the routine's entry
   address, precompute in hardware, jump to its exit. Possible — tables 4 and 5
   mean the entry points are known — but it is second-guessing code that cannot
   be read, and a wrong flag or side effect would fail subtly.
2. **It lands in the one clock domain that already misses its constraint.**
   The EU is on `clk_100`, which closes at 91.7 MHz against 100. A wide adder
   plus comparators is exactly the wrong thing to add there.
3. **It would only pay at the maximum setting**, since below it
   `clock_cycle_counter` governs and removing steps advances nothing.

**And it is not where the time is.** Hardware measurement gives 8.75 T-states per
fetched byte; the chipset resolves a read hit in 2. The remaining ~7 are inside
`mcl86_biu_max`, and they are structural rather than microcoded — its states
re-enter themselves until the emulated CPU clock edge arrives. That is bus-edge
waiting, which is what steps 1-5 above attack.

**Revisit if** the MCL86 microcode source ever becomes available. If the EU is
ever attacked directly, hardware multiply/divide and a barrel shifter — the
80186's other additions — are worth far more than the EA adder, though they hit
the same microcode problem.
